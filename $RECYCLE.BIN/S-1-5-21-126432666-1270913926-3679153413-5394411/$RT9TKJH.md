- **1.2.8** Provenance data for all components of each software release (e.g., an SBOM), must be collected,

  - **1.3** Secure development training must be provided to programmer analysts and software engineers.
    - **1.3.1** Training regarding common vulnerabilities (e.g., OWASP Top 10) and secure coding methods must be
provided to software developers upon hire and as needed thereafter. Periodic evaluations of personnel
proficiency and role-based training must be done, and needed updates to training made.
    - **1.3.2** Secure coding guidelines to develop software and services securely must be established and made
available.
  - **1.4** Secure system architecture and engineering principles must be developed and implemented for development
personnel.
    - **1.4.1** SISW must adhere to the principle of least privilege within the system architecture.
    - **1.4.2** Security must be designed within all architecture layers (front-end and back-end).
      - **1.4.2.1** Security should be considered in a multi-tiered approach spanning assets that may provide for
controls within various layers of the stack. Architecture and design must consider security as a holistic
goal with control implementation planned to span across all layers.
    - **1.4.3** Development teams should enforce peer code reviews to identify and document potential
weaknesses within systems.
    - **1.4.4** Information systems that process and store information must implement end-to-end encryption.
    - **1.4.5** SISW must harden information systems to minimize the exposure to security vulnerabilities.
  - **1.5** Secure coding principles must be developed and implemented for development personnel.
    - **1.5.1** Initial planning and preliminary development requirements and activities must consider:
      - **1.5.1.1** Validating the developers' competencies through the on boarding process and supplemental
training. Development teams must enforce the requirements of the defined secure coding principles for
all development personnel.
      - **1.5.1.2** The separation of testing and production environments to ensure data is not compromised by
any development and testing activities
      - **1.5.1.3** Using the most recent version of development tools to minimize security vulnerabilities
    - **1.5.2** Development activities must incorporate the following requirements:
      - **1.5.2.1** As part of the code review process, developers must make use of system security testing tools
to identify erroneous code that may pose a security threat
      - **1.5.2.2** Any vulnerabilities identified through the system security testing must be remediated based on
the vulnerability schedule outlined within the Siemens Industry Software (SISW) Saas Vulnerability and
Patch Management Policy
      - **1.5.2.3** Any vulnerability exceptions must be assessed with approval gained from the
CISO/management per the processes defined within the SISW Saas Vulnerability and Patch Management
Policy
      - **1.5.2.4** Development teams must prohibit the use of insecure design techniques including but not
limited to unapproved code samples
    - **1.5.3** Post development activities must incorporate the following requirements to ensure continuous
monitoring of systems:
      - **1.5.3.1** Identify, review, and remediate any potential security incidents or weaknesses
      - **1.5.3.2** Regular review of system logs for anomalous activities
      - **1.5.3.3** Periodic review of access to code repositories to prevent unauthorized access and tampering
  - **1.6** Outsourced developers must adhere to and acknowledge SISW's Secure Development Policy inclusive of
Secure System Architecture and Engineering Principles, and Secure Coding Principles.
    - **1.6.1** Where possible, SISW should consider security awareness training inclusive of secure development
training for outsourced developers.
